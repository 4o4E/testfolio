# 测试用例与结果录入

系统页面供用户只读查看。通过 `scripts/client.py` 使用本机录入接口；客户端读取 `--config` 指定的配置、`TEST_RESULTS_CONFIG` 环境变量指定的配置，或默认文件 `~/.config/test-results/client.json`，不会输出配置或令牌。接口格式和 bundle 示例见[录入接口与记录格式](references/records.md)。

## 确定本轮范围

执行 `projects`、`cases --project <编号>` 和 `runs --project <编号>`，读取目标项目的现有用例和历史结果。按照用户指定的环境、业务流程与服务版本确定本轮范围，并记录实际使用的目标环境。权限、测试数据写入及清理范围沿用用户已有授权；本系统的录入权限不代表可以修改被测系统。

根据需求、业务操作和现有接口检查用例是否完整。目录按业务流程分层，每条叶子用例包含前置条件、操作步骤和明确预期。可独立成功或失败的断言分开记录；用 `catalog --file <JSON>` 更新指定用例，编号保持稳定。需求明确但尚未验证的用例保留在目录中，状态为未测试。历史已结束轮次保留创建时的用例定义。

## 执行与保存

1. 用 `start --file <JSON>` 创建轮次，明确 `scope_case_ids`、环境、测试方式、开始时间和实际版本。记录本轮实际版本；无法确认时在 summary 说明。
2. 按用例步骤执行真实操作。浏览器测试使用真实页面并记录关键截图；接口测试记录实际请求结果；白盒审查明确哪些结论来自源码、日志或数据库。页面操作未执行时，接口成功不能证明页面操作成功。
3. 用 `artifact --file <路径>` 上传每张关键截图和必要的脱敏报告，保存返回的附件编号。每步记录操作、预期、实际观察、状态及附件。截图以操作前和结果出现后为主，省略重复等待画面；需要标记时使用 Evidence 的 `marks`，保持原图内容不变。
4. 用 `result --run <编号> --file <JSON>` 记录每个用例。通过必须覆盖本用例的全部预期；发现实际偏差记 failed；无法完成所需步骤记 blocked；尚未尝试记 not_run；不适用于本轮记 skipped 并说明原因。实际观察和证据写入 actual，不把实现推断写成已执行结果。每轮每用例只记录一次，复测创建新轮次。
5. 完成用户授权的测试资料清理，核对已有资料，然后用 `finish --run <编号> --state completed --summary <说明>` 结束轮次。无法继续则使用 interrupted，写明具体中断原因和已执行范围。completed 表示本轮工作结束，不代表所有用例通过。

用 `show --run <编号>` 重新读取，核对范围、结果数量、失败和未测试项、截图链接及清理说明。用 `link --project <项目编号> --run <轮次编号> [--case <用例编号>]` 生成对应页面链接；链接主机来自私有客户端配置。向用户说明真实失败或阻塞。仅导入旧报告时保留报告日期与原环境，不写成新测试。

凭据由被测环境的受管配置提供，报告、截图、请求正文和附件中只保存测试业务所需的脱敏内容。录入服务不保存 Cookie、密码或被测服务的访问令牌。
