# Design

## Context
镜像同时包含 Python 服务和静态网页；运行架构为 amd64／arm64，公开包已存在。实际发布中的 Node 和 Python 基础镜像多架构摘要可以沿用，依赖版本按现有发布版本锁定。参考 proposal.md 的目标。

## Decisions
- 使用既有 GHCR 包的 `buildcache-ci`、`buildcache-release` 标签保存 registry cache，采用 max 模式保留中间阶段。两种任务都读取两份缓存，主线检查与发布分别写入，避免单架构检查覆盖双架构发布缓存。相较 GitHub 缓存，registry 缓存不依赖标签间的缓存访问范围，代价是额外仓库存储。
- 主线与 PR 使用不同权限的调用任务，共用可复用检查工作流。只在可信 main 推送时授予 package 写权限、登录及导出检查缓存；PR 不授予 package 写权限、不登录、不导出。实际构建或缓存导出失败均使任务失败，不忽略错误。
- Node 阶段使用 BUILDPLATFORM，生成架构无关的网页；Python 保持目标运行架构。独立 web 检查只执行 lint 和 typecheck，网页生产构建与容器检查承接完整打包验证。
- 固定当前已发布的 Node／Python 多架构基础摘要。运行与开发依赖分别由 `.in` 声明及完整版本锁文件管理，用 uv 编译为标准 requirements 文件，安装仍使用 pip；开发锁文件约束运行锁文件，不改变既有运行依赖版本。
- 使用 COPY --link 使代码、许可证及网页层独立于前置代码层。复用依赖阶段时禁止更改依赖构建时间等无关参数；不为每次业务提交重写全部层时间戳。
- Compose 默认 missing，升级显式拉取明确版本，随后以 --pull never --no-build 启动；普通重启不访问仓库。缓存标签不能作为运行镜像。

## Risks / Trade-offs
- 首次构建和明确升级基础环境／依赖需要下载；可复用缓存必须仍存在。不能承诺每次更新完全没有网络传输。
- 冻结基础环境需要定期显式更新摘要及依赖锁文件，经 CI 后发布，不永久忽略维护更新。
- registry 缓存会保留构建中间资料；构建上下文只允许通用公开源码，不加入运行数据、凭据或私有配置。

## Migration Plan
只更新源码及自动化。先通过检查并写入冷缓存，再用相同构建输入进行第二次真实 CI，比较缓存命中、依赖层及下载／构建情况。正式版本仍为 v0.1.0；本次不创建新版本标签，不切换本机实例。回退时恢复先前 CI／Dockerfile／锁文件，现有数据库和附件不需要迁移。
